# LatencyOS 現状バグ監査レポート

**対象**: LatencyOS 0.0.5（x86_64 hard-realtime）および PulseLang 実装**実施日**: 2026-08-21**検証方式**: QEMU x86_64 / TCG、4 vCPU、128 MiB、e1000（外部通信を制限）およびNICなし構成でのブラックボックス統合テスト**結論**: **即時修正が必要な高優先度の実装不具合が4件、計測・実行状態の整合性問題が5件、仕様と実装の乖離が1件**確認された。とくにPulseLangの算術コード生成、時間単位のコンパイル、ハンドル所有権検査は、リアルタイム制御ロジックの正しさを直接損なう。

> 本レポートの「すべて」は、提供された実行バイナリ、同梱コマンド、添付仕様、QEMUで観察できる全公開操作面を対象とした意味である。カーネルのソースコード、デバッグシンボル、実機DMA/NVENC機器は未提供のため、静的解析や実機固有の全欠陥を保証するものではない。

## 2. Critical: 算術式のコード生成が壊れている（BL-01）

### 観察結果

`/pulselang/bench.pul`は以下のループを実行する。

```
$sum := 0;
$i := 0;
@while($i < 100) {
    $sum += $i * 2;
    $i += 1;
}
```

期待値は `2 × (0 + ... + 99) = 9900` である。しかし、ソース実行と明示的にコンパイルした`bench.bin`のどちらも`400`を出力した。

```
[BENCH] Iterations: 100
[RESULT] Sum:
400
```

逆アセンブルでは、乗算の左右オペランドを別レジスタに保持すべき箇所で、両方が`$r15`に割り当てられている。

```
001c: MOV  $r15, $rbx
0020: MOV  $r15, 2
0024: MUL  $r15, $r15, $r15
0028: ADD  $rdx, $rdx, $r15
```

その結果、各反復で`$i * 2`ではなく`2 * 2 = 4`が加算され、`4 × 100 = 400`になる。

### 影響

**任意の二項演算で一時レジスタが別オペランドを破壊し得る**。レイテンシー計算、輻輳制御、デッドライン判定、レート計算で誤った意思決定を起こすため、リアルタイムDSLの基盤的な正当性が失われる。

### 修正優先度と提案

**P0（出荷停止）**。式コード生成をSSA風の仮想値管理、または「評価済み左辺・右辺・結果」に必ず別の仮想レジスタを確保する方式へ変更する。少なくとも次をコンパイラ回帰試験にする。

```
@println(3 * 2);
$sum := 0; $i := 0;
@while($i < 100) { $sum += $i * 2; $i += 1; }
@println($sum); // 必ず9900
```

## 3. Critical: 時間単位サフィックスが失われる（BL-02）

### 観察結果

`filter.pul`には`$rtt > 300us`という比較がある。添付仕様では、時間リテラルはコンパイル時にナノ秒へ畳み込まれ、`300us`は`300000`になるべきである。

しかし、`filter.bin`の逆アセンブルは以下を示した。

```
0018: MOV  $r15, 300
001c: CMPGT $rax, $rax, $r15
```

実測RTTは`102395 ns`だったにもかかわらず、`102395 > 300`として輻輳扱いされ、レート60%を選択した。

```
[FILTER] Measured RTT (ns):
102395
[ACTION] Congestion detected -> Rate: 60%
```

仕様上の比較なら`102395 ns < 300000 ns`であり、100%レート側を選択すべきである。

### 影響

`ns`以外の時間単位を使う全ての`@budget`、`@wcet`、`@within`、比較条件が最大で10^9倍の誤差を持つ。デッドライン・ドロップ、輻輳制御、静的WCET表示の信頼性が失われる。

### 修正優先度と提案

**P0（出荷停止）**。Lexerで単位を保持し、AST上の`TimeLiteral { value, unit }`を`u64 ns`に畳み込む。`1us = 1_000ns`、`1ms = 1_000_000ns`、`1s = 1_000_000_000ns`の境界・桁あふれを回帰試験に含める。逆アセンブラにも単位付き定数の注釈を出すと監査可能性が上がる。

## 4. High: 線形ハンドル所有権が検証されない（BL-03）

### 観察結果

添付仕様では、`@capture()`で得た`#handle`は全ての実行パスでちょうど一度`@send()`しなければならない。しかし、次の未消費ハンドルのプログラムは`Execution Success: 0 Errors`になった。

```
#f := @capture();
```

さらに、同一ハンドルを二重送信するプログラムも成功した。

```
#f := @capture();
@send(#f);
@send(#f);
```

### 影響

DMAスロット、GPUキャプチャバッファ、e1000 TX記述子の所有権が破綻する。実装仕様どおりならコンパイル時に拒否されるべきであり、実機では二重解放、二重送信、スロット枯渇、意図しない古いフレームの送信につながる危険がある。

### 修正優先度と提案

**P0に近いP1**。コンパイラに線形状態表を導入し、ハンドルを`Available → Owned → Consumed`として追跡する。分岐合流時には両枝の状態一致を要求し、`@while`内のハンドルは反復内で消費済みであることを確認する。VM側でも`@send`済みIDを拒否する二重防御を置く。

## 5. High: 「静的に境界付けられたループ」という保証が未実装（BL-04）

### 観察結果

仕様では全ループの単調進行を静的に検証し、境界付き実行を保証するとしている。だが、次のプログラムはコンパイル段階で拒否されず、VM実行後にのみ失敗した。

```
$i := 0;
@while(1) {
    $i += 1;
}
```

実行結果:

```
ERR_PX64_WCET_EXCEEDED
Execution exceeded px64 WCET instruction step limit
STEP_LIMIT: 10,000 instruction steps
```

### 影響

「コンパイル済みコードはWCETが静的に証明済み」という主張が成り立たない。制御コアでの実行時間を上限まで消費し、リアルタイムタスクやDMA回復を遅延させる可能性がある。

### 修正優先度と提案

**P1**。`@while`をコンパイル時に解析し、比較対象、更新変数、更新方向、上限を検証する。解析不能な条件を拒否するか、`@bounded(max)`のような明示的上限を必須にする。10,000ステップ制限は二次的なフェイルセーフとして残す。

## 6. High: LatencyFSのディレクトリ解決とツリー表示が不整合（BL-05）

### 観察結果

ルートで`mkdir qa`を実行すると、`ls -l`には`qa/`が表示される。しかし、直後の相対・絶対パス移動は双方とも失敗した。

```
% mkdir qa
% cd qa
cd: qa: No such directory
% cd /qa
cd: /qa: No such directory
```

`touch inside`で生成した動的ファイルや`qa/`は`ls -l`には表示される一方、`tree`には表示されない。さらに`qa/`内相当のファイルが残った状態で`rm qa`を発行した後、プロンプトが戻らず、検証用VMを停止する必要があった。

### 影響

ユーザー空間のディレクトリ操作が実質的に不可能であり、ツールが認識するFS状態も一意ではない。非空ディレクトリ削除の無応答は、制御コンソールのDoSとなる。

### 修正優先度と提案

**P1**。`mkdir`、`ls`、`cd`、`tree`、`rm`で共通のパス正規化・inode/ディレクトリ走査実装を使う。`rm`は非再帰削除なら`Directory not empty`を即時返し、再帰削除を明示コマンドに分離する。動的FS変更を`tree`に必ず反映する回帰テストを追加する。

## 7. High: TSC周波数表示が二重化・不整合（BL-06）

### 観察結果

同一ブート中に、起動ログは`TSC Frequency: 2496 MHz`（別試行では2499 MHz）を表示した。一方、`status`と`tsc`コマンドは一貫して`3400 MHz`および`0.29 ns/cycle`を表示した。

| 表示元 | 周波数 |
| --- | --- |
| 起動時CPUID/TSC検出ログ | 2,496 MHz |
| `status` / `tsc` | 3,400 MHz |
| 差 | 36.21% |

### 影響

TSC tickからnsへの変換、`@within`判定、ベンチマーク、レイテンシーテレメトリーの値が系統的にずれる。ハードリアルタイムの根拠として使えない。

### 修正優先度と提案

**P1**。周波数ソースを一つに統一し、CPUID leaf 0x15/0x16、invariant TSC、キャリブレーション値の優先順位を明文化する。`status`、ブートログ、VM内の単位変換、WCET表示に同一の固定値または同一の校正値を渡す。校正失敗時は推定値であることを明示する。

## 8. High: SMPロール表示と実際の活動状態が一致しない（BL-07）

### 観察結果

起動時には`All 4 CPU cores successfully booted via APIC`と表示され、Core 1〜3にCapture/Encode/Networkロールが割り当てられる。しかし`cores`および`status`では、数十秒の稼働後も次の状態だった。

```
core1: Capture ... booted: true, active: false, loops: 0
core2: Encode  ... booted: true, active: false, loops: 0
core3: Network ... booted: true, active: false, loops: 0
```

`stream.pul`実行後も、`pipeline`はCapture/Encodeとも0フレーム、0レイテンシーを表示した。一方でネットワークパケット表示は増加しており、実行状態とテレメトリーの対応が取れていない。

### 影響

専用コアでのパイプライン実行という設計前提が観測上満たされない。実際にAPワーカーが停止している場合、全処理がCore 0に集中し、隔離・WCET・ジッター保証が破綻する。

### 修正優先度と提案

**P1**。AP起動完了を「APIC ACK」だけでなく、各ロールのメインループ開始・heartbeat更新まで含めて判定する。`active`、`loops`、パイプラインカウンターを同一の原子データ源から更新する。ロール開始に失敗した場合はブート成功と表示しない。

## 9. Medium: 実行テレメトリーが相互に矛盾する（BL-08）

### 観察結果

同一ブートで、以下が同時に観測された。

| コマンド | 表示 |
| --- | --- |
| `pipeline` | Capture 0 frames、Encode 0 frames、Network latency 0 ns |
| `timeline` | Capture 0 ns、Network 0 ns、E2E 1.9 µs（optimal） |
| `latency` | ヘッダのみでイベント0件 |
| `benchmark` | E2E平均 8,613 µs、最大 10,611 µs、`EXCEEDED` |
| `pipeline`（後） | network packets が48から48,048へ増加する一方、Capture/Encodeは0のまま |

### 影響

監視画面から本当のデータパス、ドロップ、遅延を判断できない。障害時に正しい原因追跡ができず、性能報告も信頼できない。

### 修正優先度と提案

**P2**。計測イベントID、時刻基準、フレームID、ring head/tail、パケットIDを統一し、`timeline`、`latency`、`pipeline`、`benchmark`が共通のイベントリングを参照するようにする。イベント未取得の場合は0nsを「成功」として描画せず、`N/A`と表示する。

## 10. Medium: ベンチマークの合否が表示最大値と一致しない実行がある（BL-09）

### 観察結果

NICなし構成で実行した1000サンプルベンチマークでは、次のように最大値が予算を超えているのに`PASS`が表示された。

| ステージ | 予算 | 表示最大値 | 表示ステータス |
| --- | --- | --- | --- |
| Input → ISR Wakeup | 50 µs | 753 µs | PASS |
| GPU Start → Capture Done | 1,700 µs | 2,220 µs | PASS |
| NVENC → Network TX Sent | 500 µs | 748 µs | PASS |

一方、e1000接続構成ではNetwork最大10,286 µsに対して`EXCEEDED`となった。したがって、合否判定は少なくとも一部構成で最大値・予算比較と一致しない。

### 影響

「PASS」を根拠にした性能保証が誤判定になり得る。

### 修正優先度と提案

**P2**。合否条件を`max <= budget`、`p99 <= budget`などに明文化し、表示した集計値と同一変数で判定する。各ステージの判定閾値・除外サンプル数・未初期化値をログに出す。

## 11. Medium: PX64のバイトコード版数が添付仕様と異なる（BL-10）

### 観察結果

添付仕様は、PX64の必須バージョンを**2**としている。一方、内蔵コンパイラが生成した`bench.bin`および`filter.bin`の逆アセンブルはどちらも`Version: 3`を表示した。

### 影響

外部ツール、テスト、バイトコード検証器、互換性保証が版数2を前提にすると相互運用性が壊れる。仕様書の文法・ABIと実装のどちらが正なのか判断できない。

### 修正優先度と提案

**P2**。実装がv3なら、ヘッダレイアウト、opcode、検証規則、移行方針を含めて仕様をv3に更新する。v2が正ならコンパイラのヘッダ出力とVM検証をv2に戻す。両方を受け入れる場合はversion-dependent decoderを明示する。

## 12. 仕様違反だが正常に働いた防御機構

以下は今回の範囲で期待どおりに動いた。修正時に退行させないこと。

| 機能 | 観察結果 |
| --- | --- |
| AES-NI要件 | AESを露出しない仮想CPUでは明示的に起動停止し、`-cpu max,+aes`では検証成功。 |
| e1000認識 | Intel 82540EM（0x8086:0x100e）を検出し、MACとMMIO BARを表示。 |
| PulseLang構文エラー | `$bad := ;`に対して行・列・オフセット・期待トークン・hex dumpを含む診断を表示。 |
| 不正バイトコード | invalid opcodeとconst-pool範囲外をVMが診断して停止。 |
| 引数処理 | `run echo.pul alpha beta gamma`が`alpha beta gamma`を出力。 |

## 13. QEMU由来の制限（製品バグとは分離）

以下は実装の問題と混同しない。

| 項目 | 観察 | 扱い |
| --- | --- | --- |
| RAPL/温度MSR | QEMUでは0を返し、OS自身も仮想化制限と表示。 | 実機で再検証が必要 |
| NVENC/物理GPU | 線形フレームバッファ初期化のみを観察。実際のNVENC完了は未確認。 | 実機またはGPUパススルーが必要 |
| ハードリアルタイム遅延 | TCGのホストスケジューリングが数ms級ジッターを持つ。 | QEMU数値を実機保証に使わない |
| NICなし時の警告 | e1000未検出・fallback表示は想定どおり。 | バグではない |

ただし、QEMU制限はBL-06〜BL-09の**表示・判定の矛盾**を免責しない。仮想化環境であっても、測定不能ならその旨を示し、`0 ns`や`optimal`で成功表示をしてはならない。

## 15. 次の検証

P0/P1修正後は、次の順に再テストするべきである。まずPulseLangの式・時間単位・線形型・ループをホスト上の決定的な単体試験にし、次にQEMUのe1000構成でコンパイラからパイプラインまでの統合試験を実行する。最後に、TSC周波数、AP heartbeat、DMA記述子、NVENC、RAPLを実機で測定する。QEMUのTCG上では「動作確認」と「安全なエラー処理」のみを判定し、マイクロ秒級の絶対レイテンシー保証には用いない。
